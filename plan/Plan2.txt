5. Ne jamais rendre visibles les métriques interdites par Plan1 :
   - raw criticality_score ;
   - ETV ;
   - FSRS ;
   - BKT ;
   - IRT ;
   - diagnostic_gap ;
   - raw WDL ;
   - Transfer Gap visible ;
   - SkillTrace mastery numérique ;
   - posterior Beta ;
   - Evidence JSON brut ;

6. Ne jamais réintroduire en V1 :
   - NeuroMonitor ;
   - brain ;

============================================================
0. THÈSE CENTRALE DU PLAN 2
============================================================

Le Plan 1 définit comment NeuroChess pense scientifiquement :

- vérité moteur ;
- Win% ;
- perte de chances ;
- score coach ;
- moments critiques ;
- training_items ;
- Practice events ;
- répétition espacée ;
- SkillTrace shadow ;
- Transfer Opportunity Model ;
- prudence sur les claims ;
- validation scientifique.

Le Plan 2 définit comment l’utilisateur vit cette science.

La mission du Plan 2 est de transformer une architecture scientifique complexe en une expérience :

- claire ;
- belle ;
- rapide ;
- calme ;
- motivante ;
- non humiliante ;
- active ;
- émotionnellement sûre ;
- accessible ;
- fluide ;
- mesurable ;
- orientée vers la prochaine action utile.

NeuroChess ne doit jamais ressembler à :

- un dashboard de métriques ;
- un clone de Stockfish ;
- un puzzle trainer générique ;
- une app de statistiques anxiogène ;
- un faux cerveau scientifique ;
- un chatbot bavard ;
- un produit qui culpabilise ;
- une app qui cache les actions importantes ;
- un logiciel où le board est décoratif.

NeuroChess doit ressembler à :

- un coach calme ;
- un laboratoire personnel de progression ;
- un carnet d’entraînement intelligent ;
- un système qui transforme les parties en actions ;
- une expérience qu’on a envie de rouvrir ;
- un espace où l’erreur est utile et non honteuse.

Phrase fondatrice UX :

NeuroChess cache la complexité,
montre l’action utile,
préserve l’envie,
et transforme chaque vraie erreur en progression.

============================================================
0.1 NORTH STAR UX
============================================================

La North Star UX de NeuroChess est :

L’utilisateur comprend quoi faire en moins de 5 secondes,
obtient une première valeur en moins de 90 secondes,
fait un effort actif en moins de 3 minutes,
et revient parce que l’expérience est claire, utile et émotionnellement sûre.

Formule UX :

Expérience NeuroChess =
clarté
× action
× confiance
× feedback
× autonomie
× plaisir
× progression visible

Si un facteur tombe à zéro, l’expérience échoue.

Exemples :

- Clarté sans action = jolie interface passive.
- Action sans feedback = frustration.
- Feedback sans autonomie = app autoritaire.
- Progression sans plaisir = abandon.
- Plaisir sans rigueur = jeu superficiel.
- Science sans empathie = utilisateur qui ne revient pas.
- Board sans interaction = frustration échiquéenne.
- Bouton sans effet visible = perte de confiance.

============================================================
0.2 PRINCIPES NON NÉGOCIABLES
============================================================

------------------------------------------------------------
0.2.1 Une action principale par état
------------------------------------------------------------

Chaque écran doit avoir :

- 1 action principale ;
- 0 à 2 actions secondaires ;
- le reste replié, masqué ou placé dans un menu avancé.

Si un écran a cinq CTA concurrents, il est faux.

------------------------------------------------------------
0.2.2 Complexité cachée, action visible
------------------------------------------------------------

L’utilisateur ne doit pas voir en V1 :

- raw criticality_score ;
- diagnostic_gap ;
- ETV ;
- FSRS ;
- BKT ;
- IRT ;
- posterior Beta ;
- Evidence JSON ;
- raw Stockfish WDL ;
- transition_weight ;
- persistence_weight ;
- reliability_weight ;
- SkillTrace mastery % ;
- Transfer Gap visible.

L’utilisateur doit voir :

- une priorité ;
- une phrase claire ;
- un exercice ;
- une correction ;
- une progression compacte ;
- une prochaine action.

------------------------------------------------------------
0.2.3 Essayer avant de voir
------------------------------------------------------------

La pédagogie active est centrale.

Dans Practice et Leçon complète :

Défi
→ Tentative
→ Micro-pause
→ Feedback
→ Correction
→ À retenir
→ Révision future

Le bouton “Voir la correction” existe, mais ne doit jamais devenir le chemin principal.

------------------------------------------------------------
0.2.4 L’erreur n’est jamais une humiliation
------------------------------------------------------------

Une erreur est :

- une donnée d’apprentissage ;
- une future révision ;
- un signal de progression.

Jamais :

- un jugement ;
- une honte ;
- une preuve d’incompétence.

------------------------------------------------------------
0.2.5 L’app ne doit jamais tourner dans le vide
------------------------------------------------------------

Interdit :

- spinner infini ;
- analyse infinie sans action ;
- état bloqué sans CTA ;
- erreur technique brute ;
- bouton qui ne répond pas ;
- board qui semble cliquable mais ne réagit pas.

Chaque état doit avoir :

- statut ;
- message ;
- action ;
- recovery ;
- debug replié si nécessaire.

------------------------------------------------------------
0.2.6 Le board doit être vivant
------------------------------------------------------------

L’échiquier est le centre émotionnel de l’app.

Il doit permettre selon le contexte :

- Review : observer, naviguer, explorer localement ;
- Practice : jouer une tentative ;
- Leçon complète : essayer puis comprendre ;
- Daily Plan : tenter les positions du jour ;
- Sandbox V1.1/V2 : tester une position librement sans IA.

Le board ne doit jamais être un décor statique incompréhensible.

------------------------------------------------------------
0.2.7 V1 n’est pas une V3 amputée
------------------------------------------------------------

V1 doit être une boucle complète minimale :

Import PGN
→ Analyse
→ Review
→ Practice
→ Attempt
→ due_at
→ Daily Plan
→ Révision
→ Progression compacte

V1 ne doit pas inclure :

- Candidate Trainer ;
- LLM coach ;
- Intent Layer profond ;
- Transfer Gap visible ;
- NeuroMonitor ;
- brain/cortex/atlas ;
- ETV visible ;
- FSRS visible.

------------------------------------------------------------
0.2.8 Les labels visibles passent par l’Action Registry
------------------------------------------------------------

Aucun label critique ne doit être inventé dans un composant.

Tous les labels d’action doivent exister dans :

- Action Registry ;
- fichier i18n français ;
- tests statiques si action critique.

Exemples d’incohérences interdites :

- “Voir Review” à un endroit et “Voir la Review” ailleurs ;
- “Réessayer analyse” à un endroit et “Reprendre l’analyse” ailleurs ;
- “Commencer” sans contexte quand plusieurs commencements existent.

============================================================
1. FONDATIONS UX ACTUELLES ET RÉFÉRENCES
============================================================

Ce Plan 2 s’appuie sur des principes UX modernes :

- visibilité du statut système ;
- contrôle et liberté utilisateur ;
- prévention des erreurs ;
- reconnaissance plutôt que rappel ;
- aide à reconnaître, diagnostiquer et récupérer des erreurs ;
- esthétique minimale ;
- accessibilité, focus visible, taille des cibles, alternative au drag/drop ;
- design tokens pour cohérence multi-écrans ;
- progressive disclosure pour cacher la complexité ;
- feedback immédiat après chaque action.

Principes obligatoires dans NeuroChess :

1. Toujours montrer l’état d’une action longue.
2. Toujours proposer une récupération.
3. Toujours permettre une action non destructive en premier dans les modales de danger.
4. Toujours fournir une alternative au drag/drop.
5. Toujours cacher le debug par défaut.
6. Toujours utiliser la langue de l’utilisateur, pas le jargon interne.

2. PERSONAS ET MOMENTS UTILISATEUR
============================================================

L’utilisateur ne pense pas en pages.

Il pense en moments.

------------------------------------------------------------
2.1 Persona A — Débutant anxieux, 400–800
------------------------------------------------------------

Pensée :

Je ne sais même pas pourquoi je perds.
J’ai peur que l’analyse me dise juste que je suis nul.

Besoin :

- sécurité émotionnelle ;
- explications simples ;
- pas de jargon ;
- petites victoires ;
- repères visuels.

UX prioritaire :

- moments très courts ;
- feedback doux ;
- pas de PV brute ;
- pas de score humiliant ;
- orientation visuelle forte ;
- module Foundations futur.

Risques :

- abandon si trop de variantes ;
- honte après mauvais score ;
- confusion sur les règles.

------------------------------------------------------------
2.2 Persona B — Joueur amateur motivé, 800–1400
------------------------------------------------------------

Pensée :

Je fais toujours les mêmes erreurs.
Je veux progresser mais je ne sais pas quoi travailler.

Besoin :

- priorité claire ;
- exercices issus de ses parties ;
- révision espacée ;
- progression visible ;
- explication courte.

UX prioritaire :

- Review simple ;
- Practice immédiate ;
- Daily Plan court ;
- phrases motivantes.

------------------------------------------------------------
2.3 Persona C — Joueur sérieux, 1400–2000
------------------------------------------------------------

Pensée :

Je veux comprendre mes patterns d’erreurs.
Je veux transférer l’entraînement en partie.

Besoin :

- moments critiques précis ;
- rejouer les décisions ;
- analyse plus profonde si demandée ;
- autonomie ;
- export ;
- exploration.

UX prioritaire :

- détails repliés ;
- exploration locale ;
- training_items durables ;
- progression par domaine prudente.

------------------------------------------------------------
2.4 Persona D — Joueur avancé, 2000+
------------------------------------------------------------

Pensée :

Je veux réduire les erreurs rares mais coûteuses.
Je veux auditer mes décisions.

Besoin :

- finesse ;
- contrôle ;
- historique ;
- recherche ;
- comparaison ;
- respect de son expertise.

UX prioritaire V1 :

- pas de faux dashboard avancé ;
- détails accessibles mais repliés ;
- export ;
- review fiable ;
- réanalyse deep optionnelle mais pas centrale.

UX future V2/V3 :

- Candidate Trainer ;
- Intent Layer ;
- Transfer Gap ;
- repertoire audit ;
- advanced review.

------------------------------------------------------------
2.5 Moments utilisateur
------------------------------------------------------------

Moments à couvrir :

- Je viens d’arriver.
- Je veux importer une partie.
- J’ai perdu et je suis frustré.
- J’ai gagné mais je veux comprendre.
- L’analyse prend du temps.
- L’analyse est bloquée.
- Ma Review est prête.
- Je veux comprendre vite.
- Je veux apprendre activement.
- Je veux essayer un coup.
- Je veux explorer une position.
- Je veux m’entraîner.
- Je veux revoir ce qui est dû.
- Je reviens après plusieurs jours.
- Je veux contrôler mes données.
- Je veux supprimer mes données.
- Je suis sur mobile.

Chaque moment doit avoir :

- état ;
- message ;
- action principale ;
- récupération ;
- test browser si critique.

3. ARCHITECTURE DE NAVIGATION
============================================================

------------------------------------------------------------
3.1 Navigation principale V1
------------------------------------------------------------

La navigation principale V1 reste exactement :

1. Aujourd’hui
2. Mes parties
3. Entraînement

Aucun quatrième onglet principal.

Interdit en V1 comme onglet principal :

- Review ;
- Progression ;
- Profil ;
- Paramètres ;
- Analyse ;
- Coach IA ;
- Cognitive Map ;
- NeuroMonitor ;
- Jouer ;
- Sandbox ;
- Foundations.

------------------------------------------------------------
3.2 Accès secondaires
------------------------------------------------------------

Profil / Paramètres :

- icône ou bouton discret en haut à droite ;
- hors navigation principale.

Import :

- action header ou carte selon contexte ;
- pas onglet principal.

Review :

- contextuelle ;
- ouverte depuis Aujourd’hui, Mes parties, Entraînement ou état Review prête ;
- pas onglet permanent.

Progression :

- carte compacte dans Aujourd’hui ;
- vue détaillée future via lien discret.

Sandbox / Jouer local :

- pas onglet V1 ;
- accessible V1.1/V2 depuis :
  - Review exploration ;
  - menu avancé ;
  - éventuel bouton “Tester une position” hors nav principale.
- ne doit pas devenir promesse principale.

Foundations :

- pas onglet V1 ;
- module V2/V3 ou onboarding futur pour 400–800.

------------------------------------------------------------
3.3 App Shell desktop
------------------------------------------------------------

Structure :

- Header 72 px.
- Logo à gauche.
- Navigation au centre.
- Actions à droite.
- Contenu max-width 1440 px.
- Padding global 24–32 px.

Header :

Gauche :
- NeuroChess
- sous-label : Chess · Decision Science

Centre :
- Aujourd’hui
- Mes parties
- Entraînement

Droite :
- Importer
- Profil / Paramètres

Règle :

- Le header doit rester calme.
- Pas de badges rouges agressifs.
- Pas de notifications anxiogènes.
- Pas d’onglet supplémentaire caché dans la nav principale.

------------------------------------------------------------
3.4 App Shell mobile
------------------------------------------------------------

Mobile :

- bottom navigation ;
- Aujourd’hui ;
- Parties ;
- Entraînement.

Profil :

- en haut à droite ;
- ou dans menu “Plus” seulement si contrainte forte.

Board / Review :

- board en haut ;
- contenu en dessous ;
- actions sticky en bas si Practice.

Practice mobile :

- mode focus plein écran ;
- nav globale masquée ou réduite ;
- CTA accessible au pouce.

------------------------------------------------------------
3.5 Zone de pouce mobile
------------------------------------------------------------

Règle :

Sur mobile, toute action principale doit être dans la zone atteignable au pouce :

- partie inférieure de l’écran ;
- CTA sticky quand l’utilisateur doit agir ;
- pas de CTA principal uniquement en haut de page.

Applications :

- Practice : Indice / Voir correction / Passer sous le board.
- Review : S’entraîner sticky après scroll.
- Import : Analyser cette partie sticky si textarea longue.
- Modal danger : Annuler et Confirmer visibles sans scroll.

------------------------------------------------------------
3.6 Règle de navigation émotionnelle
------------------------------------------------------------

L’utilisateur doit toujours savoir :

- où il est ;
- ce qu’il regarde ;
- ce qu’il peut faire maintenant ;
- comment revenir.

Chaque vue contextuelle doit avoir :

- retour visible ;
- titre clair ;
- état sauvegardé si possible ;
- pas de piège de navigation.

4.4 Motion
------------------------------------------------------------

Motion doit être :

- subtile ;
- utile ;
- rapide ;
- désactivable.

Durées :

--nc-motion-fast: 120ms;
--nc-motion-normal: 180ms;
--nc-motion-slow: 260ms;

Easing :

--nc-ease-enter: cubic-bezier(0.16, 1, 0.3, 1);
--nc-ease-exit: cubic-bezier(0.7, 0, 0.84, 0);
--nc-ease-feedback: cubic-bezier(0.34, 1.56, 0.64, 1);

Utilisations :

- transition de carte ;
- feedback correct/wrong ;
- ouverture details ;
- sélection de case ;
- progress update ;
- toast appearance ;
- modal entrance.

Interdit :

- confettis agressifs ;
- flash rouge humiliant ;
- shake violent ;
- animation longue bloquante ;
- motion obligatoire si reduced motion activé.

------------------------------------------------------------
4.5 Accessibilité de base
------------------------------------------------------------

Obligatoire :

- contraste lisible ;
- focus clavier visible ;
- target size minimum ;
- click-click en alternative au drag/drop ;
- labels ARIA sur actions critiques ;
- reduced motion ;
- mode daltonien futur ;
- board utilisable sans couleur seule ;
- texte non minuscule.

Pour le board :

- chaque case doit pouvoir avoir data-testid ou label stable ;
- les actions clavier futures doivent être possibles ;
- les coups illégaux doivent être annoncés calmement.

5. COMPONENT SYSTEM
============================================================

------------------------------------------------------------
5.1 Boutons
------------------------------------------------------------

### Primary Button

Usage :

- action principale de l’écran ;
- une seule par zone.

Exemples :

- Commencer ;
- Voir la Review ;
- S’entraîner ;
- Reprendre l’analyse.

Style :

- hauteur 44–48 px ;
- gradient cyan/blue ;
- font-weight 700 ;
- radius 12 px.

### Secondary Button

Usage :

- alternative non destructive.

Exemples :

- Importer une autre partie ;
- Voir le détail ;
- Réessayer.

### Tertiary Button

Usage :

- action discrète.

Exemples :

- Voir PGN ;
- Détails techniques ;
- Changer de format.

### Danger Button

Usage :

- suppression ;
- réinitialisation ;
- abandon session.

Règle :

- confirmation obligatoire ;
- jamais en CTA principal sauf contexte de danger zone ;
- ne reçoit pas le focus initial dans une modale.

------------------------------------------------------------
5.2 Cards
------------------------------------------------------------

Types :

- HeroCard ;
- ActionCard ;
- ReviewMomentCard ;
- TrainingEntryCard ;
- ProgressCard ;
- StateNoticeCard ;
- DangerZoneCard ;
- EmptyStateCard ;
- DemoBannerCard ;
- EngineStatusCard ;
- DataSummaryCard.

Chaque carte doit avoir :

- titre ;
- message ;
- état ;
- CTA éventuel ;
- data-testid si critique.

------------------------------------------------------------
5.3 State Notice
------------------------------------------------------------

Composant obligatoire pour états dégradés.

Props :

- variant: info | warning | danger | success ;
- title ;
- message ;
- primaryAction ;
- secondaryAction ;
- detailsCollapsed ;
- technicalDetails ;
- data-testid.

Règle :

- message humain d’abord ;
- debug replié ;
- action claire ;
- pas de stack trace visible par défaut.

------------------------------------------------------------
5.4 Disclosure
------------------------------------------------------------

Les détails techniques et avancés utilisent progressive disclosure.

Exemples :

- Voir le détail du score ;
- Détails techniques ;
- Voir PV ;
- Voir PGN ;
- Pourquoi cette position ?
- Pourquoi ce tri ?

Règle :

- fermé par défaut ;
- ouverture animée courte ;
- état mémorisé seulement si utile ;
- jamais de debug ouvert par défaut.

------------------------------------------------------------
5.5 Feedback
------------------------------------------------------------

Chaque action doit produire un feedback :

- bouton loading ;
- succès ;
- erreur ;
- état suivant.

------------------------------------------------------------
5.6 Toast System
------------------------------------------------------------

Le toast system est obligatoire.

Position desktop :

- en bas à droite ;
- max 3 toasts visibles ;
- pile verticale.

Position mobile :

- bas de l’écran ;
- au-dessus de la bottom nav ;
- jamais sous le CTA sticky.

Types :

- success ;
- info ;
- warning ;
- error.

Durées :

- success : 3 s ;
- info : 4 s ;
- warning : 5 s ;
- error : persistant ou dismissible après 6 s selon gravité.

Règles :

- toujours dismissible ;
- jamais plusieurs toasts identiques répétés ;
- pas de toast pour état critique qui mérite une carte ;
- toast = feedback court, pas diagnostic complet.

Exemples :

- “Partie importée.”
- “Export téléchargé.”
- “Session enregistrée.”
- “Tentative non enregistrée. Réessaie.”
- “Analyse mise en file.”

------------------------------------------------------------
5.7 Modal & Confirmation Pattern
Canonical marker: MODAL & CONFIRMATION PATTERN
------------------------------------------------------------

Toute action destructive utilise ce pattern.

Actions concernées :

- supprimer une partie ;
- supprimer toutes les données ;
- abandonner une session ;
- réinitialiser un mode exploration si perte de coups explorés ;
- réanalyser si cela remplace une Review visible.

Structure modale :

Titre :
- clair, action spécifique.

Message :
- expliquer ce qui sera supprimé ou perdu ;
- expliquer ce qui ne sera pas supprimé si important.

Boutons :
- bouton secondaire à gauche : Annuler ;
- bouton danger à droite : Supprimer / Confirmer.

Focus initial :
- toujours sur Annuler ;
- jamais sur action destructive.

Escape :
- ferme la modale si aucune action en cours.

Backdrop click :
- ferme seulement si non destructive faible ;
- pour suppression données, backdrop ne ferme pas ou demande Annuler visible.

Suppression de toutes les données :
- exige saisie exacte : SUPPRIMER ;
- bouton danger disabled tant que le texte n’est pas exact.

Exemple suppression partie :

Titre :
Supprimer cette partie ?

Message :
Cette partie, sa Review et ses exercices associés seront supprimés de NeuroChess.

Boutons :
Annuler
Supprimer la partie

Exemple suppression données :

Titre :
Supprimer toutes mes données ?

Message :
Cette action supprime tes parties, Reviews, exercices, tentatives, révisions, plans et inférences locales. Elle ne supprime pas les fichiers du projet.

Champ :
Tape SUPPRIMER pour confirmer.

Boutons :
Annuler
Supprimer définitivement

Toast après succès :
Données supprimées.

15. BOARD INTERACTION SPEC
============================================================

Cette section est obligatoire pour éviter que le board soit “visuellement présent mais fonctionnellement mort”.

------------------------------------------------------------
15.1 Modes du board
------------------------------------------------------------

board_mode:

review_static
review_exploration
lesson_attempt
practice_attempt
demo
sandbox

review_static :

- observer ;
- naviguer ;
- sélectionner moment ;
- pas de coup joué.

review_exploration :

- jouer localement ;
- pas de sauvegarde ;
- pas de backend attempt.

lesson_attempt / practice_attempt :

- jouer un coup ;
- envoyer attempt ;
- feedback ;
- due_at.

sandbox :

- jouer librement sans IA ;
- V1.1/V2 ;
- pas de données d’apprentissage par défaut.

------------------------------------------------------------
15.2 Click-click
------------------------------------------------------------

Obligatoire.

Flux :

1. clic source ;
2. source highlight ;
3. destinations légales highlight si disponibles ;
4. clic target ;
5. validation ;
6. action selon mode.

Same-square click :

- désélectionne.

Click illegal target :

- message calme ;
- sélection conservée ou reset selon ergonomie ;
- pas de crash.

------------------------------------------------------------
15.3 Drag/drop
------------------------------------------------------------

Optionnel mais recommandé.

Comportement :

- ghost piece pendant drag ;
- source highlight ;
- destinations légales highlight si disponibles ;
- snap to square si legal ;
- retour animé si drop illégal ;
- drop hors board = annulation ;
- Escape pendant drag = annulation si supporté.

Règle accessibilité :

drag/drop ne doit jamais être le seul moyen de jouer.

------------------------------------------------------------
15.4 Promotion
------------------------------------------------------------

V1 minimum :

- si promotion apparaît en Practice, proposer promotion dame par défaut ;
- ou afficher une limitation claire si non supportée.

V1.1/V2 :

- popup promotion :
  Dame
  Tour
  Fou
  Cavalier

Règle :

pas de crash sur promotion.

------------------------------------------------------------
15.5 Orientation
------------------------------------------------------------

Review :

- orientation selon user_color si connue ;
- sinon blanc par défaut.

Practice :

- orientation selon side_to_move ou user_color selon contrat produit ;
- jamais orientation qui rend le coup attendu inversé.

Option future :

- bouton discret “Retourner l’échiquier”.

------------------------------------------------------------
15.6 Haptics mobile
------------------------------------------------------------

V1.1/V2 si supporté :

- coup correct : pulse court ;
- coup illégal : double pulse court ;
- session terminée : pulse doux long.

Règle :

désactivable via préférences.

------------------------------------------------------------
15.7 Board keyboard future
------------------------------------------------------------

V1 minimum :

- focus visible sur board ;
- pas de piège clavier.

V1.1 :

- sélection par coordonnées ;
- arrow navigation ;
- Enter select ;
- Escape cancel.

43. DEFINITION OF DONE UX
============================================================

Une fonctionnalité UX est done seulement si :

1. l’utilisateur comprend l’action principale ;
2. état vide existe ;
3. état loading existe ;
4. état erreur existe ;
5. recovery existe ;
6. feedback existe après action ;
7. mobile minimal fonctionne ;
8. keyboard/focus minimal fonctionne ;
9. no forbidden metrics visible ;
10. no fake-science copy ;
11. browser smoke couvre le flow ;
12. docs mises à jour ;
13. strings centralisées ;
14. data-testid stable si flow critique ;
15. toast ou state notice prévu si action async ;
16. modal confirmation prévue si destructif ;
17. empty state présent si absence de données ;
18. reduced motion respecté si animation ;
19. performance budget respecté ou feedback immédiat ;
20. Plan1 constraints vérifiées.
